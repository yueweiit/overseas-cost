# Frappe 架构设计：海外采购综合成本核算模块 V1.0

更新时间：2026-07-07

## 1. 文档目标

本文档基于当前已确认的 ERP 技术栈，输出“海外采购综合成本核算模块”在 ERP 中的推荐架构设计，作为后续 Frappe / ERPNext 开发落地的基础。

当前已确认技术栈：

1. 后端：`Python + Frappe Framework`
2. 前端：`JavaScript、Vue`
3. 数据库：`MariaDB`

本文档重点回答：

1. 模块在 Frappe 中应如何组织
2. 一期海运场景应如何分层
3. 计算、导入、版本、留痕、ERP 回写分别放在哪一层
4. 什么先做，什么后做

---

## 2. 设计原则

### 2.1 先做核算闭环，再做深度集成

一期目标不是把整个海外采购流程重做一遍，而是先把“墨西哥海运综合成本核算”这条链路跑通。

一期先解决：

1. Excel / 单据导入
2. 报关单 / 运单 / SKU 聚合
3. 费用归集
4. 分摊规则
5. 暂估版 / 实际版
6. 重算
7. 修改留痕
8. 最终回写 ERP 成本

### 2.2 前端按 Excel 列顺序直展示，后端按领域对象建模

虽然页面要求按 Excel `A ~ BE` 列顺序直接展示，但后端绝不能只按“列号”硬编码。

后端必须按业务对象建模：

1. 批次
2. 版本
3. 物料明细
4. 分摊规则
5. 附件解析
6. 审计日志

### 2.3 一期只做海运，但结构必须兼容空运/快递

一期业务范围：

1. 运输方式只启用 `海运`
2. 页面可预留 `空运 / 快递` 入口
3. 后端字段和 DocType 要支持未来扩展，不要写死为海运专属表

### 2.4 人工可修正，但系统必须保留证据链

这是财务核算系统，不是纯自动算表工具。

所以：

1. 允许修改
2. 允许重新试算
3. 允许暂估转实际
4. 但每次修改、切版、重算都必须留痕

## 3. 推荐 Frappe 模块组织方式

## 3.1 建议新建独立 Custom App

建议在 ERP 中新建一个自定义 app，例如：

`overseas_costing`

原因：

1. 不建议把业务直接散落到现有 ERPNext 标准模块里
2. 成本核算逻辑较重，后续还可能继续扩展
3. 独立 app 更方便维护、迁移和版本管理

推荐 app 层级如下：

```text
overseas_costing/
  overseas_costing/
    config/
    overseas_costing/
      doctype/
        overseas_cost_batch/
        overseas_cost_version/
        overseas_cost_item/
        overseas_cost_allocation_rule/
        overseas_cost_attachment/
        overseas_cost_audit_log/
      page/
        overseas_cost_workbench/
      api/
        batch.py
        import_api.py
        calculate.py
        writeback.py
      services/
        import_service.py
        calculate_service.py
        allocation_service.py
        version_service.py
        audit_service.py
        attachment_parse_service.py
      utils/
        field_mapper.py
        currency.py
        validators.py
```

## 4. 分层设计

建议按 5 层组织：

## 4.1 展示层

载体：

1. Frappe Page
2. Vue 页面
3. DataTable / 自定义查询页

职责：

1. 按 Excel 列顺序展示
2. 提供筛选、导入、编辑、重算、版本切换
3. 展示审计日志、差异对比

说明：

1. 页面不要直接写复杂计算
2. 页面只负责展示和调用 API

## 4.2 API 层

载体：

1. `frappe.whitelist()` 方法
2. `overseas_costing/api/*.py`

职责：

1. 暴露批次查询接口
2. 暴露导入接口
3. 暴露重算接口
4. 暴露版本切换接口
5. 暴露 ERP 回写接口

说明：

1. API 层不直接写复杂业务
2. 只做参数校验、权限校验、结果封装

## 4.3 领域服务层

载体：

1. `services/*.py`

职责：

1. 导入解析
2. 成本试算
3. 分摊规则执行
4. 版本复制与切换
5. 审计日志记录
6. ERP 回写准备

这是整个模块的核心层。

## 4.4 数据层

载体：

1. Frappe DocType
2. MariaDB 表

职责：

1. 存批次主单
2. 存版本
3. 存 SKU 明细
4. 存分摊规则
5. 存附件解析结果
6. 存审计日志

## 4.5 集成层

职责：

1. 对接 ERP 标准采购/库存单据
2. 对接附件上传
3. 对接回写接口
4. 后续对接 AI 单据解析

一期建议先预留，不做深度绑定。

## 5. 一期推荐功能边界

## 5.1 一期必须做

1. 海运批次导入
2. 2026 年 Yuewei 主表字段落表
3. 报关单号 / 运单号 / SKU 聚合
4. Excel 列顺序展示
5. 暂估版 / 实际版
6. 修改留痕
7. 重新试算
8. 导出

## 5.2 一期建议预留，但可不完全做深

1. 附件解析框架
2. 完税凭证识别入口
3. ERP 回写状态字段
4. 空运 / 快递枚举
5. 按体积分摊

## 5.3 一期先不做

1. 电商业务独立页面
2. 全自动无人复核回写
3. 复杂工作流审批
4. 所有国家和所有运输模式统一上线

---

## 6. 推荐运行流程

## 6.1 主流程

1. 用户导入 Excel / 物流成本文件
2. 系统生成批次主单
3. 系统生成默认暂估版
4. 系统落表 SKU 明细
5. 系统加载默认分摊规则
6. 系统执行试算
7. 用户人工修正部分字段
8. 系统记录修改日志
9. 用户再次重算
10. 用户确认生成实际版
11. 系统预留回写 ERP 成本

## 6.2 附件扩展流程

1. 上传商业发票 / 完税凭证 / 运费账单
2. 系统保存附件
3. 后续 AI 解析服务提取关键字段
4. 写回到批次或费用明细
5. 再次触发重算

## 8. 推荐技术实现方式

## 8.1 Frappe 侧

建议使用：

1. `DocType` 作为主数据模型
2. `Page` 作为自定义工作页
3. `frappe.call` 或 REST 作为前端调用方式
4. `frappe.enqueue` 处理大文件导入和重算任务

## 8.2 Vue 侧

如果前端用 Vue：

1. Vue 负责筛选栏、表格编辑、版本切换
2. 实际数据由 Frappe API 提供
3. 页面可作为 Frappe Page 内嵌前端组件

## 8.3 MariaDB 侧

1. 主数据使用标准 DocType 表
2. 大量列顺序字段建议分“主字段 + JSON 扩展字段”
3. 对高频筛选字段单独建索引

---

## 9. 异常处理设计

必须明确以下状态：

1. 导入失败
2. 字段缺失
3. 运单未匹配
4. 报关单未匹配
5. 汇率缺失
6. 分摊规则不完整
7. 重算失败
8. 回写 ERP 失败

建议所有异常都沉淀到：

1. 页面提示
2. 批次状态
3. 审计日志

## 10. 一期最推荐的开发顺序

### 第一步

先建 Custom App 骨架。

### 第二步

先建核心 6 个 DocType。

### 第三步

做批次导入 + 明细落表。

### 第四步

做默认分摊规则 + 重算引擎。

### 第五步

做详情页整表展示。

### 第六步

做版本切换、修改留痕、差异追踪。

### 第七步

最后再补 ERP 回写和附件解析。

---

## 11. 一句话结论

当前最合理的 Frappe 架构不是“先做很多页面”，而是：

1. 先建独立 `Custom App`
2. 先建稳定的 `DocType + 重算服务`
3. 页面只做展示与操作壳
4. 后续再逐步接入 ERP 原生采购/库存链路
